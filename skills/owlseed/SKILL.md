# owlseed

owlseedは、AIエージェントがプロジェクト内で継続的かつ一貫して活動するための、不変の行動原則とライフサイクルを定める単一のSkillである。

owlseedはプロジェクト固有の知識・手順・状態を持たない。それらはowlseedを起点にプロジェクト内で生成される**コアSkill**と**派生Skill**、および**状態**と**AGENTS.md**へ委ねる。owlseedが固定するのは「名前と契約」だけであり、パス・形式・手段は固定しない。

owlseed自身は読み取り専用として扱う。改善したいことが見つかったら、それはコアSkillか派生Skillの改善であって、owlseedの書き換えではない。owlseedを書き換えると、すべてのプロジェクトの基準が動いてしまう。

## 用語

- **コアSkill** — `owlseed-compass` / `owlseed-state` / `owlseed-verify` / `owlseed-grow` の4つ。名前は固定。発芽時に `references/contracts/` の契約から生成される。中身はプロジェクト固有で、経験により改善される。
- **派生Skill** — プロジェクトが必要に応じて生むSkill。名前は自由。本文冒頭に前文（`references/preamble.md`）を持つ。
- **外部Skill** — 前文を持たないSkill。実行段階で直接は使わず、`owlseed-grow` が派生Skillとして取り込んだ形でのみ使う。
- **作業単位** — ライフサイクルを1周する単位。1セッションで検証まで到達できる大きさにする。
- **層** — L1: コアと派生Skill / L2: 状態（`owlseed-state` が所有）/ L3: AGENTS.md（プロジェクト理解）。owlseedはL0。

## 読んだら最初にすること

1. コアSkillが4つ揃っているか確認する。
2. 揃っていなければ**発芽**へ進む。揃っていれば**定位**へ進む。
3. 人間から依頼を受けている場合も、直接着手しない。依頼はまず `owlseed-state` へ作業単位として登録し、`owlseed-compass` で目的・範囲に沿うか確認した上で**選択**へ進む。こうすると、対話で受けた依頼と自律的に選んだ作業が同じ道を通り、途中でセッションが切れても復帰できる。

## ライフサイクル

発芽は初回のみ。以降は定位→収束を1作業単位ごとに回す。状態は各段階で逐次更新する。各段階の詳細と判断に迷った時の指針は `references/lifecycle.md` を読む。

| 段階 | 問い | 呼ぶSkill | 守ること |
|---|---|---|---|
| 発芽 Germinate | 目的・状態・検証手段はどこにあるか | grow → compass / state / verify を生成 | コアSkillが揃うまで作業を始めない。目的が読み取れなければ人間に確認する |
| 定位 Orient | 今どこにいるか。土台は壊れていないか | state, verify, compass | 壊れた土台の上で新規作業を始めない。修復を作業単位として先に積む |
| 選択 Select | 次の1単位は何か。目的に沿うか | state, compass | 1回1単位。1セッションで検証まで到達できる大きさにする |
| 実行 Act | 必要な能力はあるか。無ければ作る価値があるか | 派生Skill, grow | owlseedを変更しない。目的・検証契約を黙って変えず、変更は決定として記録する |
| 検証 Verify | 検証済みと言えるか。根拠は何か | verify | 根拠なしに検証済みにしない。失敗なら実行へ戻すか単位を分割する |
| 沈殿 Sediment | この経験はどの層へ返すか | grow | L1変更は受入ゲートを通す。L3は提案として反映。owlseedと重複する規範は削除する |
| 収束 Close | 次の自分が復帰できる形か | state | 未記録の作業途中を残して終わらない |

実行中に改善点を見つけたら、今の作業結果に影響するか、後回しにすると手戻りが出るかで振り分ける。影響するなら即時に反映し、そうでなければ `owlseed-state` の沈殿待ちに積み、沈殿で処理する。

## コアSkillの呼び方

名前で呼ぶ。ランタイムの機能で読めない場合は、`name: owlseed-<役割>` を持つ SKILL.md を探して読む。

契約は `references/contracts/` にある。契約が定めるのは「保証すべきこと」と「禁止」だけで、手順は定めない。手順はプロジェクトのものであり、発芽後にプロジェクトが埋め、経験で改善する。

## 優先順位と従属

owlseed ＞ コア ＞ 派生。矛盾を見つけたら上位に従い、矛盾そのものを `owlseed-state` に記録する。記録された矛盾は下位Skillの改善材料になる。

従属関係はdescriptionではなく、本文冒頭の前文で表す。descriptionは発見のための場所であり、そこに従属を書くとタスクと一致せず選ばれなくなる。

## 実行段階で使える能力

前文を持つSkillだけを使う。前文の有無で「ハーネスの一部か」が判別でき、外部Skillの更新やインターフェース変更にハーネス全体が引きずられない。外部Skillを使いたければ `owlseed-grow` に取り込みを求める。取り込みは薄いアダプタ（前文＋いつ使うか＋制約）から始めてよい。

## 受入ゲート（要約）

L1のあらゆる変更（形成・改訂・統合・廃止・版移行の再構成）は7条件を満たす。詳細と判定手続きは `references/gate.md`。

1. 根拠がある — どの作業単位の結果から生じた変更か記録できる
2. 反復性か保持価値 — 2回以上現れた、または独立した能力として保持する価値がある
3. 保証を壊さない — コアなら契約を満たし続け、派生なら過去に通った検証が通る
4. 過剰適応でない — 契機となった具体例を伏せても記述が成立する
5. 層が正しい — 状態はL2へ、プロジェクト理解はL3へ
6. owlseedを侵害しない — owlseedと矛盾せず、owlseedを変更していない
7. 可逆 — 変更前へ戻せる状態で行う

判定はできる限り実行可能な検証を根拠にする。無ければ理由を `owlseed-state` の決定履歴に残し、人間が後から監査できるようにする。

## 層の境界規則

- 名前のついた再利用可能な手順はL1、「いつ何が起きたか」はL2。
- L3にはプロジェクト理解だけを置く。規範が混入していればowlseedと重複するものは削除し、プロジェクト固有の規範はL3に残す。手順はL1へ、状態はL2へ移す。
- L3は人間も読むため、整理は作業終了時に提案として反映する。
- owlseedはL1/L2/L3の中身を知らない。

## owlseedがしないこと

パスの固定、状態の形式の固定、検証手段の指定、サブエージェントの運用方法、コンテキスト圧縮の方法、権限モデルの実装、派生Skillの汎用Skillへの昇格。これらはランタイムかプロジェクトか人間の領域である。委譲に関してowlseedが持つ原則は一つだけ: 委譲しても検証は省けない。

## 版

現在の版: 0.1.0（仮）。契約の名前変更・統合・分割はメジャーバージョンでのみ行う。プロジェクトが記録しているowlseedの版と現在の版が異なる場合は `references/migration.md` に従う。
