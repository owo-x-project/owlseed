# Grow

Read this when you make, take in, combine or remove a skill. Every change passes references/gate.md.

## Making a derived skill

Copy assets/derived.md and fill it in. A runtime's own tool for making skills may shape the file, nothing more. End the description with the two words "Under owlseed". Put the relation to owlseed in the note at the top, not in the description. Keep the body short. As advice, not a rule: owlseed keeps its own SKILL.md under 1,100 words and each reference under 500. Make sure no angle brackets remain. Name the skill under Kinds of work unit in owlseed-compass. A skill that is not named there is never called.

## Taking in an outside skill

Take in an outside skill when a human chooses it, or when you have used it more than once. A human's choice is a decision. Record it; it is the proof for the gate.
Copy the body of the outside skill under the note from assets/derived.md. Do not change its words. A change of words at intake is a change without proof. Write the description in the owlseed form, and name the skill under Kinds of work unit in owlseed-compass.
Where the copy disagrees with a core skill, the core skill wins, and you record the disagreement. Do not edit the copy to fix it in advance. The copy changes later, one piece of proof at a time: what it says about done moves to owlseed-compass, what it says about checking moves to owlseed-verify, and the body shrinks until only the procedure is left.
Parts of the copy that belong in owlseed-compass, owlseed-verify, owlseed-state or the project's notes for agents stay in the copy for now. Record each part as an improvement item, with the place it belongs. That meets gate condition 5 for the copy.
A tool that cannot be copied, such as a server or a command, is taken in by pointing at it: write its name, where it is, how to use it in this project, and its limits.
The body holds only what is needed to run the skill.

## Scripts in a skill

Consider a script for a mechanical step that repeats. The text of a script costs no context; only its output does. Do not write a script for something that must be rewritten for every job. A script has tests, and the tests are the proof for gate condition 3. Write one line in the skill that says what the script does, so that a runtime that cannot run it can do the step by hand.

## Combining and removing

Combining and removing skills pass the gate. When you remove a skill, read condition 3 as "another skill still provides this ability". Run again the recorded checks of the skills you touched and of the skills you may remove. Running all recorded checks again is a work unit of its own. If results still look fine but recorded checks start to fail, the ability is broken.
