# 受入ゲート

L1（コアSkill・派生Skill）のあらゆる変更に適用する。形成・改訂・統合・廃止・版移行の再構成・外部Skillの取り込み。コアと派生で条件は同じ。人間承認が必要かどうかは `owlseed-compass` の判断権限の境界がプロジェクトごとに決める。

## 7条件

### 1. 根拠がある

どの作業単位の結果から生じた変更か記録できる。推測や「あった方がよさそう」だけで変えない。会話の中の思いつきは、作業単位の結果になってから根拠になる。

### 2. 反復性か保持価値

2回以上現れた、または独立した能力として保持する価値がある。1回限りの手順を切り出すと、使われないSkillが増え、descriptionの選択精度が落ちる。外部Skillの取り込みは「外部依存の記録」として保持価値ありと判定してよい。

### 3. 保証を壊さない

コアSkillなら、契約の「保証すべきこと」を変更後も満たす。派生Skillなら、`owlseed-verify` が記録している過去の検証が変更後も通る。実行可能な検証があればそれを根拠にする。

### 4. 過剰適応でない

契機となった具体例（値・パス・固有名・その時だけの事情）を伏せても、Skillの記述が成立する。成立しなければ、それは手順ではなく事例であり、L2（決定履歴）に置く。

### 5. 層が正しい

状態・履歴・「いつ何が起きたか」が混入していればL2へ。プロジェクトの構造・スタック・制約の説明が混入していればL3へ。Skillには手順だけを残す。

### 6. owlseedを侵害しない

owlseedの規範と矛盾しない。owlseed自体を変更していない。`owlseed-grow` 自身の改訂で最も破られやすい条件なので、grow改訂時は特に確認する。

### 7. 可逆

変更前へ戻せる状態で行う。`owlseed-state` の復旧手順に接続できること。

## 判定手続き

1. 変更の内容と根拠（条件1）を書き出す
2. 条件2〜7を一つずつ確認し、根拠を書く
3. 条件3は、実行可能な検証があれば実行結果を根拠にする。無ければ判定理由を明記する
4. 判定結果と理由を `owlseed-state` の決定履歴に記録する
5. 通過したら反映し、前文を付ける（`preamble.md`）

自己判定は繰り返すほど甘くなる傾向がある。実行可能な検証を優先し、無い場合は人間が後から監査できる記録を残す。

## 記録の形（例）

```
変更: <Skill名> を <形成|改訂|統合|廃止|再構成>
根拠: <作業単位の参照>
条件1〜7: <各条件の判定と理由>
検証: <実行した検証と結果、または「実行可能な検証なし。理由: …」>
判定: <通過|保留|却下>
```

## 剪定

沈殿のたびに、使われていないSkillと重複するSkillを候補に挙げる。似たdescriptionのSkillが増えると、ランタイムがどれを選ぶか不安定になる。統合・廃止も同じ7条件を通す（廃止の場合、条件3は「その能力が別のSkillで引き続き満たされる」と読む）。
