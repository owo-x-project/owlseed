# 推奨知見（規範ではない）

ここに書くものはowlseedの規範ではない。プロジェクトが状態の形式や検証手段を初めて決める時に参照できる、根拠のある推奨である。採用しなくてもowlseedに違反しない。より良い方法があれば置き換えてよい。

## 状態（owlseed-state）について

- **作業単位の一覧は、AIが勝手に書き換えにくい形式にする** — Anthropicの長時間実行ハーネスの実験では、Markdownより JSON の方がモデルが不適切に改変しにくかった。状態フィールドの変更だけを許し、項目の削除・編集を禁じる文言も効いた
- **開始時に進捗記録とバージョン管理の履歴を読む** — 前回どこまで進んだかを再構成する最短の手段
- **区切りごとにコミットする** — 復旧手順が「戻せる点」を必要とする
- **初期化スクリプトを持つ** — 開発サーバーの起動などをスクリプト化すると、毎セッションの「動かし方の再発見」が消える

## 検証（owlseed-verify）について

- **基本確認を短く持つ** — セッション開始時に土台が壊れていないかを数分で確かめられる手順（起動して1つ操作する程度）
- **人間が使うように確かめる** — 単体テストやcurlだけでは、実際に使った時の壊れ方を見逃す。UIがあるならUIから確認する
- **生成と評価を分ける** — 同じ文脈で生成と評価をすると甘くなる。別セッションやサブエージェントで評価するか、少なくとも要件を読み直してから評価する

## Skill（owlseed-grow）について

- **descriptionは「いつ使うか」を先頭に、具体的な状況語で** — descriptionが選択の唯一の手がかり。末尾は切り捨てられうる
- **SKILL.md本文は500行以内、詳細はreferences/へ** — 本文は起動のたびに全部読まれる
- **似た能力は1つに統合する** — 似たdescriptionが並ぶと選択が不安定になる
- **一度しか使わない手順は切り出さない** — 使われないSkillはdescriptionの税だけを払い続ける

## ライフサイクルについて

- **1セッション1単位** — 一度に多くをやろうとして途中で切れると、次のセッションが半端な状態を推測することになる
- **進捗を見て完了を宣言しない** — 一覧に残っている単位が終わるまで終わっていない
- **壊れた状態で終えない** — 次のセッションが修復から始まると、修復と新規作業の原因が混ざる
