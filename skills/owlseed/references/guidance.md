# 推奨知見

ここに書くものはowlseedの規範ではない。プロジェクトが形式や手段を初めて決める時に参照できる、根拠のある推奨である。採用しなくてもowlseedに違反しない。より良い方法があれば置き換えてよい。

## 状態

- 作業単位の一覧は、AIが勝手に書き換えにくい形式にする。Markdownより JSON の方がモデルが不適切に改変しにくかった実験がある。項目の集合を固定し、値の更新だけで進めると、長時間の作業で状態が崩れにくい
- 現在位置の要約は一覧と分けて小さく保つ。段階ごとに読まれるため、大きいと毎回のコストになる
- 区切りごとにコミットする。復旧手順が戻せる点を必要とする
- 初期化スクリプトを持つと、毎セッションの「動かし方の再発見」が消える

## 検証

- 基本確認を短く持つ。起動して1つ操作する程度で、土台が壊れていないかを数分で確かめられるもの
- 生成と評価を分ける。同じ文脈で生成と評価をすると甘くなる

## Skill

- descriptionは「いつ使うか」を状況語で先頭に書く。descriptionが選択の唯一の手がかりであり、末尾は切り捨てられうる
- 本文は短く保つ。owlseedの実装は本文600語、referencesを各400語以内に収めている。同程度を目安にするとよい。これはモデルの前提に依存する数字なので、モデルが変われば見直してよい
- 複写した骨組みに角括弧が残っていないか確認する。frontmatterの角括弧は仕様違反であり、ランタイムがロードを拒否しうる

## スクリプト

- 繰り返す機械的な手順はスクリプト化を検討する。スクリプトの中身はコンテキストを消費せず、出力だけが入る
- 作業のたびに書き換えが必要なものはスクリプトにしない。無理な汎化もしない
- スクリプトを持つSkillはテストを持ち、受入ゲートの条件3の実行可能な根拠にする
- 言語はプロジェクトの規約に従う。規約が無ければ POSIX sh と POSIX awk が最も移植性が高い
- SKILL.md にそのスクリプトが何をするかを1行書く。実行できないランタイムでも手でなぞれる
